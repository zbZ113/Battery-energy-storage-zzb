该工程的技术路线是长什么样子的？每一个大框架下的核心作用是什么？
## 一句话看懂技术路线

这个工程的核心路线不是“让大模型直接预测电池寿命”，而是：

> **真实电池数据 → 数据治理 → 早期循环特征 → 寿命/退化模型 → 不确定性与物理核验 → 可信工具封装 → 多 Agent 编排 → API、前端和协同决策。**

其中：

* **模型负责算数值；**
* **工具层负责证明数值从哪里来；**
* **Agent 负责组织调用顺序；**
* **LLM 只负责理解任务和解释结果；**
* **前端、飞书、MCP 负责把结果送到人手里。**

这也是项目反复强调的原则：数值权威属于数值工具，不属于 LLM；PyBaMM 只做短期物理参考，不冒充真实长期寿命。

# 二、每一个大框架的核心作用

## 1. 数据接入层：把各种来源的数据接进来

### 涉及的数据源

* MATR 电芯循环数据；
* HUST 电池数据；
* Naumann 循环老化和日历老化数据；
* 用户上传的 Canonical CSV；
* 未来的 BMS、EMS、MQTT、Modbus 数据。

### 核心作用

这一层只负责：

> **把外部世界的数据安全地带进系统。**

它不应该直接训练模型，也不应该在这里计算寿命。

因为不同数据集存在非常大的格式差异：

* MATLAB HDF5；
* ZIP、pickle 或 Excel；
* 循环编号定义不同；
* 容量、电流、时间单位不同；
* EOL 标签含义不同；
* 电芯 ID 命名方式不同。

因此项目为不同数据源建立单独的适配器，而不是让后续模型直接读取原始文件。架构文档将 MATR、HUST、Naumann 和 BMS/EMS 都归入接入层。

### 输入与输出

```text
输入：
原始 MAT / HDF5 / ZIP / Excel / CSV / BMS 数据

输出：
经过安全读取、具有来源信息的原始记录
```

### 这一层最重要的原则

**接入不等于信任。**

外部文件必须先检查：

* 文件大小；
* 文件头；
* SHA-256；
* 清单记录；
* 允许的格式；
* 是否存在危险反序列化；
* 来源和授权信息。

项目明确排除了原始电池文件、模型制品和运行结果直接进入 Git，并通过 manifest 管理来源。

---

## 2. 数据治理与标准化层：把杂乱数据变成可训练资产

这是整个工程最重要、也最容易被低估的一层。

### 核心作用

> **统一数据语义，并防止模型因为数据错误或泄漏得到虚假好成绩。**

主要包括：

1. 统一电芯、循环和采样点结构；
2. 统一容量、电压、电流、温度、时间单位；
3. 检查循环缺失、时间倒退、异常跳变和重复记录；
4. 明确 EOL 和 cycle-life 标签含义；
5. 按电芯划分训练、验证、校准和测试集合；
6. 为数据、划分和处理结果生成版本和哈希。

README 描述的数据底座包括 JSON 元数据、Parquet 数组、内容寻址制品、质量审计和按 `cell_id` 完全隔离的数据划分。

### 为什么必须按电芯划分

不能把同一块电芯的前 50 个循环放入训练集、后 50 个循环放入测试集。

否则模型实际上已经看过该电芯的特征，会造成严重数据泄漏。

项目采用：

```text
train cell IDs
validation cell IDs
calibration cell IDs
test cell IDs
```

四组互斥划分。三批 MATR 的划分清单中也明确列出了不同电芯 ID。

### 输入与输出

```text
输入：
不同来源的原始记录

输出：
Canonical 数据集
质量报告
数据版本
电芯划分清单
来源及文件哈希
```

### 它不负责什么

这一层不负责判断模型好不好，只负责保证：

> **送进模型的数据是可信、统一并且没有明显泄漏的。**

---

## 3. 特征工程层：从早期循环中提取可预测信号

原始电压、电流和容量曲线不能直接全部扔给普通模型。

特征工程层负责将早期电池行为转换为模型能使用的表示。

### 主要特征路线

#### 传统统计特征

可能包括：

* 初始容量；
* 容量下降斜率；
* 容量变化方差；
* 内阻变化；
* 温度变化；
* 充放电时间；
* 协议参数；
* 早期循环之间的差值。

这些主要供 Variance 和 XGBoost 使用。

#### ΔQ(V) 特征

比较不同循环下：

```text
容量—电压曲线的差值
```

例如第 100 循环与第 10 循环的容量曲线差异。

这类特征是 MATR 电池寿命预测中的经典思路，用来捕获早期曲线中不明显但与后续寿命相关的变化。

#### 曲线张量

CPMLP 使用：

```text
电芯 × 循环 × 固定电压网格
```

形式的输入。

电压轴先插值到统一网格，不存在的循环使用显式 mask，而不是把缺失值错误地当成容量零。CPMLP 实现会检查被标记为缺失的曲线必须保持 NaN，只有应用 mask 后才能替换成网络所需的填充值。

### 输入与输出

```text
输入：
Canonical 循环与采样点数据

输出：
传统统计特征表
ΔQ(V) 特征
曲线张量
特征版本号
```

### 核心价值

这一层解决的是：

> **如何从仅有的前 20、50、100 或 150 个循环中，找到能够预示完整寿命的变化。**

# 三、数值模型层

这是实际产生寿命和退化数值的地方。

## 4.1 Dummy 模型：最低基线

### 核心作用

Dummy 模型通常预测训练集寿命的平均值或中位数。

它不追求优秀，而是回答：

> **复杂模型到底有没有比“所有电芯猜同一个寿命”更好？**

如果 XGBoost 或 CPMLP 连 Dummy 都打不过，说明复杂模型没有意义。

---

## 4.2 Variance 模型：经典早期寿命基线

### 核心作用

使用早期容量曲线变化的方差等少量特征进行回归。

它是一个较简单、可解释的电池寿命预测基线。

优点：

* 特征少；
* 训练快；
* 容易解释；
* 适合检验数据处理是否正确。

缺点：

* 表达能力有限；
* 对工况和数据分布变化敏感；
* 难以利用完整曲线结构。

训练编排中 Dummy 和 Variance 都作为静态基线存在，并分别在验证、校准和测试集合上进行预测。

---

## 4.3 XGBoost：表格特征主力模型

### 核心作用

> **从容量、温度、内阻、协议和 ΔQ(V) 等结构化特征中学习非线性关系。**

XGBoost 适合该项目的原因：

* 数据规模相对有限；
* 输入主要是表格特征；
* 对非线性和特征交互建模能力较强；
* 可以输出特征重要性；
* 比深度模型更容易训练和调试。

训练脚本配置了：

* 最多 2000 轮；
* 验证集早停；
* 固定随机种子；
* GPU 训练；
* UBJ 模型制品；
* 测试集和校准集独立预测。

---

## 4.4 CPMLP：直接学习早期曲线表示

CPMLP 可以理解为两级 MLP。

### 第一级：单循环编码器

对每个循环的容量—电压曲线进行编码：

```text
电压网格上的容量曲线
        ↓
Cycle Encoder MLP
        ↓
该循环的隐藏表示
```

### 第二级：跨循环聚合

再把多个早期循环的表示聚合：

```text
循环1表示
循环2表示
循环3表示
……
    ↓
带 mask 的平均聚合
    ↓
Aggregation MLP
    ↓
预测 EOL80
```

### 核心作用

> **让模型直接从曲线形状中学习寿命信息，而不是完全依赖人工设计的统计特征。**

### 特别设计

项目中的 CPMLP 有几个明显约束：

* 缺失循环必须有显式 mask；
* 缺失曲线不能伪装成零容量；
* 每个样本至少有一条观测曲线；
* 训练电芯必须属于训练集；
* 输出通过 `softplus` 限制在截止循环之后；
* 数据、特征、划分和模型版本必须一致。

---

## 4.5 混合退化模型：预测完整 SOH 轨迹

前几个模型主要回答：

```text
这块电芯最终大约能活多少循环？
```

混合退化模型则回答：

```text
从当前循环开始，它的 SOH 将怎样逐步下降？
```

### 核心作用

输出一条单调下降的 SOH 轨迹，例如：

```text
Cycle 100 → SOH 0.96
Cycle 200 → SOH 0.92
Cycle 300 → SOH 0.87
Cycle 400 → SOH 0.81
Cycle 430 → SOH 0.80
```

RUL 不单独凭空回归，而是由预测轨迹第一次越过 EOL 阈值时推导：

```text
RUL = 首次越过阈值的循环 - 当前循环
```

### 为什么强调单调性

普通神经网络可能预测出：

```text
SOH 0.90 → 0.88 → 0.91 → 0.85
```

即电池容量突然“恢复”。

项目通过正值趋势项和累计非负退化增量，尽量保证预测轨迹具有单调退化性质。README 对此进行了明确说明。

# 四、可信与自适应层

## 5.1 Conformal Prediction：给预测加可信区间

单点预测：

```text
预测寿命 = 850 循环
```

对工程决策通常不够。

Conformal 输出类似：

```text
预测寿命 = 850
90% 区间 = [730, 980]
```

### 核心作用

> **告诉使用者模型有多不确定。**

主要指标：

* **PICP**：真实结果落入区间的比例；
* **MPIW**：预测区间平均宽度。

一个区间覆盖率高但特别宽，也没有太大决策价值。因此需要同时评价覆盖率与宽度。

### 为什么单独有 calibration 集

Conformal 校准不能使用训练集，也不应偷看测试集，所以系统设置独立的校准电芯集合。

技术流程是：

```text
训练集 → 训练模型
验证集 → 选择模型、早停
校准集 → 估计误差分位数
测试集 → 最终评价区间覆盖率
```

训练编排中会分别产生测试预测和校准预测，再构造寿命区间。

---

## 5.2 在线校正：随着新循环到达更新个体判断

当一块电芯又运行了几十个循环，系统不应该一直沿用最初判断。

### 核心作用

> **吸收该电芯的新观测，修正个体退化轨迹。**

但项目不主张线上随意重训整个全局模型，而是：

* 冻结全局模型；
* 更新个体偏置；
* 更新退化速率；
* 更新拐点等个体参数。

这样可以避免少量新数据破坏全局模型。

可以理解为：

```text
全局模型：学习所有电芯共有规律
个体参数：适应该块电芯自身差异
```

---

## 5.3 CORAL / DANN：处理跨数据集迁移

MATR 上训练得好，不代表在 HUST 或真实储能场景中也好。

原因包括：

* 电芯化学体系不同；
* 充放电协议不同；
* 温度不同；
* 采样频率不同；
* 仪器不同；
* 标签定义不同。

### CORAL

通过对齐源域和目标域特征的统计分布，减少两者之间的协方差差异。

核心作用：

> **让 MATR 特征空间更接近目标数据集特征空间。**

### DANN

使用域分类器和梯度反转，使特征提取器学习：

```text
能预测寿命
但难以判断数据来自哪个数据集
```

核心作用：

> **学习相对域不变的电池退化表示。**

不过需要注意，仓库当前训练入口明确表明 HUST 和 Naumann 的正式 Canonical 数据与目标语义尚未准备好，因此这部分目前更接近已有组件和技术路线，而不是完整验证完毕的跨域成果。

# 五、主动试验与物理核验层

## 6.1 Gaussian Process 主动试验

电池老化实验成本很高，不可能把所有组合都完整跑一遍。

实验条件可能包括：

```text
温度
平均 SOC
DOD
充电倍率
放电倍率
```

### 核心作用

> **推荐下一组最值得做的实验。**

Gaussian Process 会输出：

* 某个工况下退化指标的预测均值；
* 预测不确定性。

系统再综合考虑：

* 信息增益；
* 试验耗时；
* 设备成本；
* 安全边界；
* 是否与已有试验重复。

最终选择：

```text
预期信息增益 / 时间与成本
```

较高的候选试验。

它解决的不是“这块电池还能活多久”，而是：

> **实验室下一步应该优先测试什么工况？**

---

## 6.2 PyBaMM：短期物理边界检查

PyBaMM 是电化学电池仿真框架。

该项目计划使用：

* SPMe 模型；
* Prada2013 参数集；
* Experiment 工况描述。

### 核心作用

验证某种运行条件在短期内是否表现出明显物理风险，例如：

* 电压是否越界；
* 电流是否过高；
* SOC 是否达到边界；
* 是否提前终止；
* 工况在物理上是否合理。

### 它不负责什么

PyBaMM 在这个项目里**不负责制造长期寿命标签**。

也就是说，不能因为 PyBaMM 模拟了 10 个循环，就声称得到了真实 1000 循环寿命。

它的角色只是：

```text
数据模型：负责长期寿命推断
PyBaMM：负责短期物理一致性和边界参考
```

项目章程明确要求 PyBaMM 输出标记为 `SIMULATED` 或 `PHYSICS_REFERENCE`。

# 六、可信工具与审计层

这是该工程区别于普通机器学习项目的核心工程设计。

## 7.1 ToolRegistry：统一管理数值能力

所有数值能力都被包装成标准工具，例如：

```text
validate_battery_data
extract_early_cycle_features
predict_cycle_life
predict_soh_trajectory
calibrate_prediction_interval
update_cell_parameters
check_operating_condition
recommend_next_experiment
make_batch_decision
generate_audited_report
```

### 核心作用

> **统一模型、Agent、API、MCP 和前端调用数值能力的方式。**

而不是让：

* 前端自己算一遍；
* Agent 自己写一套逻辑；
* API 再复制一套；
* Streamlit 又做一套。

`ToolRegistry` 会检查：

* 工具是否已注册；
* 调用角色是否有权限；
* 输入是否符合 Pydantic 模式；
* 工具版本是否一致；
* 返回结果是否为 `ToolResult`；
* 输入哈希是否匹配；
* 模型、数据和特征版本是否为空；
* 是否包含 provenance。

---

## 7.2 ToolResult：每一个数值的身份证

模型输出不是简单返回：

```json
{"life": 850}
```

而是返回类似：

```text
result_id
tool_name
tool_version
input_hash
model_version
data_version
feature_version
created_at
values
warnings
provenance
```

### 核心作用

> **让每一个正式数字都能回答“谁算的、用什么算的、输入是什么、版本是什么”。**

这样报告里出现“预计寿命 850 循环”时，可以追溯到：

```text
哪个数据版本
哪个特征版本
哪个模型版本
哪个输入电芯
哪个工具版本
哪一次运行
```

---

## 7.3 AuditLedger：保存证据链

### 核心作用

保存所有经过验证的工具结果，并建立结果之间的引用关系。

例如：

```text
质量检查结果 A
       ↓
特征提取结果 B
       ↓
寿命预测结果 C
       ↓
区间校准结果 D
       ↓
批次决策结果 E
       ↓
报告结果 F
```

报告不能自己重新输入一个新的寿命数字，只能引用已存在的结果。

# 七、多智能体层

这个项目的 Agent 并不是多个聊天机器人自由讨论，而是多个受限工作角色。

## 8.1 数据质检 Agent

### 核心作用

负责：

* 检查数据 Schema；
* 检查异常循环；
* 检查划分；
* 检查泄漏；
* 生成数据质量结论。

它不能调用寿命决策工具，更不能擅自下达使用建议。

---

## 8.2 寿命预测 Agent

### 核心作用

组织：

* 特征结果；
* 寿命模型；
* SOH 轨迹；
* Conformal 区间；
* 在线校正。

它只消费经过登记的数据、模型和结果。

---

## 8.3 物理核验 Agent

### 核心作用

调用 PyBaMM 或工况检查工具，检查：

* 倍率；
* SOC；
* 电压；
* 电流；
* 终止条件；
* 物理边界风险。

---

## 8.4 试验决策 Agent

### 核心作用

根据：

* 当前工况覆盖情况；
* 模型不确定性；
* 试验成本；
* 信息增益；
* 安全限制；

推荐下一组试验。

---

## 8.5 监督器

监督器是整个 Agent 系统中真正有控制权的部分。

### 核心作用

1. 理解用户目标；
2. 生成工具调用计划；
3. 检查 Agent 是否越权；
4. 检查每一步依赖是否满足；
5. 检查结果来源；
6. 遇到证据不足时降级；
7. 对正式决策要求人工确认。

监督器代码对可规划工具、输入字段、结果引用和角色权限都进行了本地白名单限制。即使 LLM 给出非法调用计划，也会回退到确定性计划。

### LangGraph 的作用

LangGraph 在这里用于构建状态机，例如：

```text
接收任务
  ↓
意图识别
  ↓
数据质检
  ↓
特征提取
  ↓
寿命预测
  ↓
区间校准
  ↓
物理核验
  ↓
批次决策
  ↓
人工审批
  ↓
报告生成
```

它主要管理：

* 当前执行到哪一步；
* 前一步结果 ID；
* 是否失败；
* 是否重试；
* 是否等待人工确认；
* 中断后如何恢复。

# 八、服务与产品层

## 9.1 FastAPI：统一后端接口

### 核心作用

将工具能力暴露为 HTTP API。

项目中定义的领域路由包括：

```text
/v1/analyses/quality
/v1/predictions/lifetime
/v1/predictions/trajectory
/v1/predictions/update
/v1/physics/check
/v1/experiments/recommend
/v1/decisions/batch
```

FastAPI 本身不负责重新实现模型，只调用共享的 `ToolInvocationService`。

### 额外职责

* 用户认证；
* 角色权限；
* 项目管理；
* 数据集登记；
* 实验登记；
* 模型制品登记；
* Agent 运行；
* 报告下载；
* 飞书事件接收。

---

## 9.2 Next.js：正式业务门户

### 核心作用

面向普通业务用户、项目成员和评委。

主要承载：

* 登录；
* 项目列表；
* 数据集；
* Agent 任务；
* 寿命预测结果；
* 可信区间；
* 审计证据；
* 报告查看。

前端采用 Next.js 16、React 19、TypeScript，并通过 FastAPI 获取项目和结果数据。

---

## 9.3 Streamlit：科研分析工作台

### 核心作用

面向算法和实验人员快速：

* 查看电池曲线；
* 调整实验参数；
* 检查特征；
* 比较模型；
* 查看训练结果；
* 做研究分析。

它不应该另写一套预测算法，而是通过 HTTP 调用共享后端。

可以理解为：

```text
Next.js：正式产品界面
Streamlit：算法研究与内部实验界面
```

---

## 9.4 MCP：让外部 AI 客户端调用工具

### 核心作用

将已注册的电池工具通过 MCP 暴露给支持 MCP 的客户端。

例如外部助手可以请求：

```text
检查这批电芯数据
预测该电芯寿命
生成审计报告
```

但 MCP 客户端不能越过：

* 工具白名单；
* 模型版本校验；
* 输入模式；
* 审计链；
* 权限控制。

---

## 9.5 飞书：研发协同出口

### 核心作用

把模型结果变成团队任务流：

```text
发现异常
  ↓
飞书发出告警
  ↓
创建复检任务
  ↓
分发审计报告
  ↓
发起人工审批
  ↓
审批结果回写系统
```

飞书本身不计算 SOH 或寿命，只传递：

* 任务状态；
* `run_id`；
* `result_id`；
* 报告引用；
* 审批动作。

---

## 9.6 MQTT / Modbus / BMS / EMS 沙箱

### 核心作用

模拟工业设备接入。

* MQTT：接收 BMS 测量批次；
* Modbus：模拟寄存器协议；
* BMS 接口：上传容量、电压、电流等观测；
* EMS 接口：消费已经审计的决策结果。

但项目的定位是“决策支持”，不能绕过现有 BMS/EMS 安全联锁直接控制设备。

# 十、一次完整任务实际怎样流动

假设用户上传一块电芯的前 100 个循环，并请求寿命分析。

## 第一步：数据接入

```text
上传 CSV / BMS 数据
```

系统检查格式、大小和身份权限。

## 第二步：数据质检

调用：

```text
validate_battery_data
```

输出：

```text
质量是否通过
缺失循环
异常跳变
警告
quality_result_id
```

## 第三步：特征提取

调用：

```text
extract_early_cycle_features
```

生成：

```text
容量趋势
内阻趋势
ΔQ(V)
曲线张量
feature_result_id
```

## 第四步：寿命预测

调用：

```text
predict_cycle_life
```

模型可能是 XGBoost 或 CPMLP，输出：

```text
预测寿命
model_version
prediction_result_id
```

## 第五步：区间校准

调用：

```text
calibrate_prediction_interval
```

得到：

```text
预测值 850
区间 [730, 980]
interval_result_id
```

## 第六步：SOH 轨迹和 RUL

调用：

```text
predict_soh_trajectory
```

生成完整退化轨迹，并从首次跨过 EOL 阈值的位置推导 RUL。

## 第七步：物理检查

调用：

```text
check_operating_condition
```

判断当前倍率、SOC 和温度是否存在明显物理风险。

## 第八步：决策

调用：

```text
make_batch_decision
```

规则综合：

* 数据质量；
* 寿命；
* 区间宽度；
* 是否域外；
* 物理风险；
* 业务策略。

输出枚举可能是：

```text
ACCEPT
RECHECK
DOWNGRADE
REJECT
```

## 第九步：报告与协同

调用：

```text
generate_audited_report
```

报告只引用前面已经登记的结果 ID，再通过：

* Next.js 展示；
* PDF/DOCX 下载；
* 飞书分发；
* MCP 查询。

# 十一、这条技术路线最核心的三个设计思想

## 1. 数值计算与 LLM 分离

```text
LLM：理解、规划、解释
模型工具：计算
规则：决策
```

避免大模型直接编造寿命和 SOH。

## 2. 所有结果都必须可追溯

每一个数字都绑定：

```text
数据版本
特征版本
模型版本
工具版本
输入哈希
结果 ID
来源信息
```

## 3. 预测、物理和决策各司其职

```text
数据模型：回答可能如何退化
Conformal：回答有多不确定
PyBaMM：回答短期物理上是否合理
规则引擎：回答业务上如何处理
Agent：组织这些步骤
```

这套路线在思想上是合理的。它的问题不在技术结构，而在于目前铺得过大：**MATR 主训练链是当前最实的一条，跨数据集、完整 Agent、基础设施和工业协同仍有不少属于正在贯通或下一阶段能力。**仓库训练入口目前也只允许 MATR 和三批 MATR 真正执行，HUST 与 Naumann 会明确返回尚未准备完成。
